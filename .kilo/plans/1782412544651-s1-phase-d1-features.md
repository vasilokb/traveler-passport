## 0. Главное архитектурное решение — «DOM vs pure»

Roadmap утверждает: «features НЕ знают про DOM» и «не могут импортировать из widgets/ или app/». Но 4 из 5 перечисленных feature содержат DOM-тяжёлые функции (по реальному коду `main.js`):

| Функция (по roadmap) | Строки main.js | DOM-операции |
|---|---|---|
| `renderStampOverlay` | 365–402 | `innerHTML`, `getElementById`, `addEventListener` |
| `goToCollection` | 409–442 | `setState`, `switchTab`, `scrollIntoView`, `classList` |
| `openDatePicker` | 1388–1414 | `innerHTML`, `addEventListener`, `style.display` |
| `buildSearchResults` | 561–602 | Возвращает HTML-string (принимает state) |
| `buildFilterAccordions` | 604–703 | Возвращает HTML-string (принимает state) |
| `toggleSight` | 973–1046 | `setState` + `updateMapMarkers/Filter`, `patchChecklistInPlace`, `querySelectorAll` |
| `togglePlanned` | 931–971 | `setState` + `saveNote` + `rerenderCityCard` + `updateMap` |
| `confirmVisit` | 1420–1448 | `setState` + `closeDatePicker` + `rerenderCityCard` + `updateMap` |
| `removeVisit` | 1450–1473 | `setState` + `closeCityCard` + `renderProfile` + `updateMap` |

**Чистое решение** (распилить каждую на pure-logic + render-callback) раздувает скоуп в 2 раза и дублирует Phase D2. **Принятое решение — прагматичный split:**

### Что живёт в features/

| Категория | Примеры | Почему |
|---|---|---|
| **State mutation** (immutable update + `store.setState`) | `confirmVisit`, `removeVisit`, `toggleSight`, `togglePlanned` — тела setState | Чистая бизнес-логика |
| **Feature-self-contained UI** (модалки, overlay'ы) | `openDatePicker`, `closeDatePicker`, `renderStampOverlay`, `closeStampOverlay`, `showShareText` | Интринсичны действию, нет смысла выносить в widgets |
| **Pure HTML-string renderers** (state → string) | `buildSearchResults`, `buildFilterAccordions` | Принимают state, возвращают string; DOM-mutation (innerHTML) остаётся в main.js |
| **Pure helpers** (state → state) | `addMilestone`, `removeMilestone`, `removeAllMilestones` | Уже pure в `src/lib/milestones.js`, переезжают |

### Что НЕ живёт в features/

| Категория | Примеры | Почему |
|---|---|---|
| **Ambient rendering** (рендер других виджетов) | `rerenderCityCard`, `patchChecklist`, `updateMapMarkers/Filter`, `renderProfile`, `closeCityCard`, `switchTab` | Эти функции рендерят ЧУЖИЕ области UI; features получают их как **hooks** через `init(store, hooks)` |

### Render hooks контракт

```js
// main.js передаёт в features при init():
const hooks = {
  rerenderCityCard(cityId),       // toggleSight, togglePlanned, confirmVisit
  patchChecklist(cityId, sightId), // toggleSight (optimistic UI)
  updateMap(),                    // toggleSight, togglePlanned, confirmVisit, removeVisit
  renderProfile(),                // removeVisit
  closeCityCard(),                // removeVisit, goToCollection
  switchTab(tabId),               // goToCollection
  saveNoteNow(cityId),            // confirmVisit, toggleSight, togglePlanned
  showStampOverlay(cityId),       // confirmVisit (после setState)
  withMux(fn),                    // debounce обёртка (400ms)
  withMuxSlow(fn),                // 560ms для toggleSight
};
```

**Контракт:** hooks — это «канал связи вниз», который Phase D2 заменит на subscribe-based auto-render. Features вызывают `hooks.updateMap()` вместо `updateMapMarkers(); updateMapFilter()` (это одна логическая операция).

### Что остаётся в main.js (до Phase D2)

- **Render-функции виджетов** (рендер своих областей): `renderPassport`, `renderCityCard`, `renderChecklist`, `renderProfile`, `initMapPoints`, `updateMapMarkers`, `updateMapFilter`, `updateMapViewBox`, `zoomAtPoint`, `resetMapZoom`, `renderOnboarding`
- **Tab/onboarding логика**: `switchTab`, `openCityCard`, `closeCityCard`, `startEditName`/`saveEditName`/`cancelEditName`, `handleOnboardingContinue`/`handleOnboardingSkip`
- **Delegated event handlers**: `handlePassportClick`, search debounce, map wheel/pinch/touch
- **Глобалы**: `mapPointsInitialized`, `isProcessing`, `noteDebounceTimer`, `currentPassportMode`, `suppressMapClick`, `mapViewBox`, `MAP_ORIG_VB`
- **`init()` bootstrap**: создаёт store, инициализирует features, регистрирует обработчики

После D1 main.js ~1500 строк (Phase D2 разнесёт виджеты → ~30 строк).

## 2. Render Hooks — детальный контракт

### 2.1. Структура `hooks`

```js
// main.js (в init(), после создания store)
const hooks = {
  rerenderCityCard(cityId) {
    rerenderCityCardPreservingScroll(cityId);
  },
  patchChecklist(cityId, sightId) {
    patchChecklistInPlace(cityId, sightId);
  },
  updateMap() {
    if (mapPointsInitialized) {
      updateMapMarkers();
      updateMapFilter();
    }
  },
  renderProfile() {
    renderProfile();
  },
  closeCityCard() {
    closeCityCard();
  },
  switchTab(tabId) {
    switchTab(tabId);
  },
  saveNoteNow(cityId) {
    var noteEl = document.getElementById("city-card-note");
    if (noteEl) saveNote(cityId, noteEl.value);
  },
  showStampOverlay(cityId) {
    // ⚠️ renderStampOverlay требует callbacks onShare/onCollection.
    // main.js передаёт их как closure на stampsApi (module-level, см. §5.4).
    renderStampOverlay(cityId, stampsApi.showShareText, stampsApi.goToCollection);
  },
  withMux(fn) {
    return function (...args) {
      if (isProcessing) return;
      isProcessing = true;
      try { return fn.apply(this, args); }
      finally { setTimeout(function () { isProcessing = false; }, 400); }
    };
  },
  withMuxSlow(fn) {
    return function (...args) {
      if (isProcessing) return;
      isProcessing = true;
      try { return fn.apply(this, args); }
      finally { setTimeout(function () { isProcessing = false; }, 560); }
    };
  },
};
```

### 2.2. Поведение hooks

| Hook | Семантика | Что внутри |
|---|---|---|
| `rerenderCityCard(cityId)` | Полный ре-рендер city-card с сохранением scroll | `rerenderCityCardPreservingScroll(cityId)` |
| `patchChecklist(cityId, sightId)` | Оптимистичный патч одного пункта чек-листа | `patchChecklistInPlace(cityId, sightId)` |
| `updateMap()` | Обновить маркеры карты + фильтр. No-op если карта не инициализирована | `if (mapPointsInitialized) { updateMapMarkers(); updateMapFilter(); }` |
| `renderProfile()` | Полный ре-рендер профиля | `renderProfile()` |
| `closeCityCard()` | Закрыть city-card overlay | `closeCityCard()` |
| `switchTab(tabId)` | Переключить вкладку | `switchTab(tabId)` |
| `saveNoteNow(cityId)` | Принудительное сохранение заметки из textarea | Читает `#city-card-note` → `saveNote()` |
| `showStampOverlay(cityId)` | Показать stamp-overlay после confirmVisit | `renderStampOverlay(cityId)` |
| `withMux(fn)` / `withMuxSlow(fn)` | Обёртка для `isProcessing` (400/560ms) | Проверяет и сбрасывает мьютекс |

### 2.3. Контракт features

- Features **НИКОГДА** не вызывают render-функции main.js напрямую — только через hooks.
- Если feature нуждается в новом hook — это **сигнал** для пересмотра дизайна в код-ревью.
- Hooks вызываются **синхронно** (как и render-функции сейчас). `setTimeout` для отложенного rerender остаётся внутри feature (как в текущем `toggleSight` line 1037).

## 4. `init(store, hooks)` — паттерн

### 4.1. Унифицированный контракт

Каждый feature экспортирует:
```js
export function init(store, hooks) {
  // ... регистрация ...
  return {
    // public methods (для вызова из main.js render-функций)
    // пример: search.getResultsHtml()
  };
}
```

**Особый случай — `features/search/`**: возвращает `{ getResultsHtml, getAccordionsHtml }` — pure-функции, вызываемые из `renderPassport` в main.js.

**Особый случай — `features/visit/`**: возвращает `{ confirmVisit, removeVisit }`. Они используются как callbacks в DOM handlers: date-picker confirm button → `visitApi.confirmVisit`. Для этого `main.js` после `initVisit` передаёт `visitApi.confirmVisit` в `renderDatePicker(cityId, onConfirm)`.

**Особый случай — `features/stamps/`**: возвращает `{ goToCollection, showShareText }` — используются как callbacks в `renderStampOverlay`. Аналогично: `renderStampOverlay(cityId, stampsApi.showShareText, stampsApi.goToCollection)`.

### 4.2. Обработка `isProcessing`

`isProcessing` — глобальный мьютекс, блокирует на 400мс (560мс для toggleSight). В Phase D1 он остаётся глобальным в main.js (перенести в features сложно без циклов). main.js экспортирует `withMux`/`withMuxSlow` через hooks (см. § 2.1).

**Принятое упрощение:** Phase D1 сохраняет `isProcessing` в main.js. Phase D2 пересмотрит (возможно, per-feature processing flag).

**Новый код в main.js (Phase D1 вводит):**

`withMux` и `withMuxSlow` НЕ существуют в текущем коде — Phase D1 создаёт их как helper'ы в main.js:

```js
// main.js (новый код Phase D1)
function withMux(fn) {
  return function (...args) {
    if (isProcessing) return;
    isProcessing = true;
    try { return fn.apply(this, args); }
    finally { setTimeout(function () { isProcessing = false; }, 400); }
  };
}
function withMuxSlow(fn) {
  return function (...args) {
    if (isProcessing) return;
    isProcessing = true;
    try { return fn.apply(this, args); }
    finally { setTimeout(function () { isProcessing = false; }, 560); }
  };
}
```

Эти функции — обёртки над `isProcessing`. Они инкапсулируют паттерн «взять мьютекс → выполнить → освободить через N мс», который сейчас дублируется в `togglePlanned`/`confirmVisit`/`removeVisit`/`toggleSight`. Phase D1 централизует его через features.

### 5.4. Новый `init()` блок

**ВАЖНО: closure scope.** Feature APIs (`visitApi`, `stampsApi`, etc.) нужны не только в `init()`, но и в `renderCityCard`, `renderPassport`, и других render-функциях, которые вызываются ПОСЛЕ `init()` (через tab switch, openCityCard, и т.п.). Чтобы render-функции могли ссылаться на feature API, **API должны быть объявлены на module-уровне** (не как локальные переменные `init()`).

```js
// main.js — module-level declarations
let visitApi, checklistApi, planApi, stampsApi, searchApi;

function init() {
  // ... обработчики tab-bar, passport, map (как было) ...

  // === Инициализация features (присваивание module-level переменных) ===
  visitApi = initVisit(store, {
    rerenderCityCard: rerenderCityCardPreservingScroll,
    updateMap: function () {
      if (mapPointsInitialized) { updateMapMarkers(); updateMapFilter(); }
    },
    renderProfile: renderProfile,
    closeCityCard: closeCityCard,
    saveNoteNow: function (cityId) {
      var noteEl = document.getElementById("city-card-note");
      if (noteEl) saveNote(cityId, noteEl.value);
    },
    // ⚠️ Wrapper: renderStampOverlay требует callbacks onShare/onCollection.
    // stampsApi — module-level переменная (объявлена через `let stampsApi;`),
    // которая будет инициализирована далее в этом же init().
    // Closure гарантирует, что stampsApi будет доступен при ВЫЗОВЕ (после init).
    showStampOverlay: function (cityId) {
      renderStampOverlay(cityId, stampsApi.showShareText, stampsApi.goToCollection);
    },
    withMux: withMux,
    withMuxSlow: withMuxSlow,

  checklistApi = initChecklist(store, {
    rerenderCityCard: rerenderCityCardPreservingScroll,
    patchChecklist: patchChecklistInPlace,
    updateMap: function () {

    withMux: withMux,
    withMuxSlow: withMuxSlow,
  });

      var noteEl = document.getElementById("city-card-note");

    switchTab: switchTab,
    closeCityCard: closeCityCard,
  });

  searchApi = initSearch(store, {});  // hooks пока не нужны

  // === Обновлённые обработчики (используют feature API) ===
  // renderCityCard использует visitApi.confirmVisit, planApi.togglePlanned,
  // checklistApi.toggleSight — все через renderDatePicker/onclick handlers.
```

**Расширение `tools/check-imports.mjs`:**

Текущий `allowed()` (строки 103-119 в `tools/check-imports.mjs`) для `case 'features':` возвращает `true` — т.е. features могут импортировать **всё**. Это слишком разрешительно для Phase D1.

**⚠️ ВАЖНО: `layerOf()` возвращает `'app'` для ЛЮБОГО файла в `src/app/`**, включая `app/store.js` и `app/main.js`. Поэтому простой `to === 'app'` НЕ различает их — это пропустит features → app/main.js (что ЗАПРЕЩЕНО FSD).

**Рекомендуемый вариант (строгий)** — отдельный `if` для features с явной проверкой конкретного файла:

```js
// В файле tools/check-imports.mjs — после основного цикла проверки,
// добавить второй проход ТОЛЬКО для features:
for (const file of files) {
  const layer = layerOf(file);
  if (layer !== 'features') continue;
  const src = await readFile(file, 'utf8');
  let m;
  IMPORT_RE.lastIndex = 0;
  while ((m = IMPORT_RE.exec(src)) !== null) {
    const spec = m[1];
    const target = resolveImport(spec, file);
    if (!target) continue; // npm-пакет
    const targetLayer = layerOf(target);
    const targetRel = path.relative(SRC, target).replace(/\\/g, '/');
    
    // Допустимо: shared, entities, app/store.js (singleton)
    // path.basename() чтобы работало и для `@app/store` и для `@app/store.js`
    const allowedFeatures =
      targetLayer === 'shared' ||
      targetLayer === 'entities' ||
      (targetLayer === 'app' && path.basename(target) === 'store.js');
    
    if (!allowedFeatures) {
      violations.push({
        file: path.relative(ROOT, file).replace(/\\/g, '/'),
        spec,
        from: 'features',
        to: targetLayer,
        target: targetRel,
      });
    }
  }
}
```

Этот код проходит ТОЛЬКО по feature-файлам и применяет правила:
- ✅ features → shared (entities, lib, dom, format, etc.)
- ✅ features → entities (city, region, sight)
- ✅ features → app/store.js (для `store.setState`)
- ❌ features → features/X (X — другой feature, например visit → checklist)
- ❌ features → widgets (пока не существует, но заблокировано)
- ❌ features → lib (transitional, но заблокировано)
- ❌ features → app/main.js (явно запрещено — main инициализирует features, а не наоборот)

**Альтернативный подход (более строгий через `allowed()`)** — НЕ рекомендуется, потому что требует рефакторинга `layerOf()` для возврата более специфичных имён (например, `'app/store'` vs `'app/main'`). Это усложняет код без выигрыша.

### §17. Зафиксированные отклонения (deviations) от v3

**D-1: Bugfix — `renderStampOverlay` подключается к `confirmVisit` (мёртвый код в v3).**

Grep по **оригинальному** `app.js` (до Phase A): `renderStampOverlay` определена (строка 403), но **вызывается 0 раз** — мёртвый код. Это **существующий баг v3**, не регрессия Phase C. `app-description_v3.md §6.22` ошибочно описывает confirmVisit как «показывает stamp-overlay» — документация расходится с кодом.

Phase D1 **исправляет** этот баг: `confirmVisit` (через hook `showStampOverlay`) вызывает `renderStampOverlay(cityId, onShare, onCollection)`. Это **новое поведение** относительно v3 — пользователь впервые увидит анимацию штампа после подтверждения визита. Smoke-чеклист пункт 3 теперь реально проверяет появление штампа.

> ⚠️ **Для агента-исполнителя:** `app-description_v3.md §6.22` — НЕ источник истины для confirmVisit. Реальный код (v3 `app.js` и Phase C `main.js`) — источник истины. Оригинал НЕ вызывает `renderStampOverlay` нигде. D1 добавляет этот вызов как bugfix.

## 12. Риски и меры

| Риск | Вероятность | Мера |
|---|---|---|
| **Циклические зависимости между features** (visit нужен stamps overlay, stamps нужен visit для confirmVisit) | Средняя | Hooks: callbacks передаются через `init(store, hooks)` — features не импортируют друг друга |
| **`renderStampOverlay` живёт в features/stamps, но вызывается из `visitApi.confirmVisit`** | Высокая (уже разрешена) | Hook `showStampOverlay` импортирует `renderStampOverlay` в main.js и передаёт в initVisit |
| **`isProcessing` глобал нарушает инкапсуляцию features** | Средняя | Принятое упрощение для D1; Phase D2 пересмотрит (возможно, per-feature processing flag) |
| **Feature тесты требуют mocks для hooks** — boilerplate | Низкая | Helper `createHooks()` в `tests/setup.js` создаёт моки для всех hooks |
| **main.js потеряет прямой доступ к внутренностям features** (e.g., `addMilestone` теперь в `features/checklist/milestones.js`) | Низкая | main.js не нуждается в прямом доступе — всё через store и hooks |
| **Большой diff в main.js (~250 строк удалено, ~50 добавлено)** | Средняя | Делать по блокам: сначала visit, потом checklist, потом plan, потом stamps, потом search |
| **`renderPassport` всё ещё большой (логика фильтрации остаётся в нём)** | Низкая | Phase D2 распилит `renderPassport` в widgets/passport/ |
| **`renderStampOverlay` принимает callbacks** — изменение API может сломать вызывающий код | Низкая | Изменение в одном месте (city-card confirmVisit flow) — единичная правка |

## 13. Связь с Phase D2

Phase D1 закладывает API, которое Phase D2 пересмотрит:

| Phase D1 (текущая) | Phase D2 |
|---|---|
| Hooks передаются в `init(store, hooks)` | `store.subscribe()` → виджеты подписываются на нужные части state |
| `hooks.updateMap()` после мутации | Auto-rerender через `store.subscribe(state => updateMap())` |
| `hooks.rerenderCityCard(cityId)` | Auto-rerender через `store.subscribe(state => { if (state.activeOverlayCityId === cityId) renderCityCard(cityId); })` |
| `renderPassport`/`renderCityCard` в main.js | `widgets/passport/` + `widgets/city-card/` |
| `main.js` ~1500 строк | `main.js` ~30 строк (только `init()` bootstrap: `initStore × N` + switchTab + SW) |

Имена функций, экспортируемых в Phase D1 features, **сохраняются** при переезде в widgets (Phase D2). Это контракт.
