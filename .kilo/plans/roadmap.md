# Единый план развития: S1 (Фундамент) + S2 (Монетизация) + дорожная карта S3–S6+

> **Дата:** 2026-06-25 · **Статус:** финальный план
> **На основе:** `refactor-and-notes.md`, `monetization.md`, `app-description_v3.md`, `docs/architecture.md`.
> **Назначение плана:** превратить монолит из 2227 строк в модульную архитектуру, способную принять платный контент (аудиогиды) без переписывания ядра. План объясняет не только **что** делается на каждом шаге, но и **зачем** — чтобы через полгода было понятно, почему принято то или иное решение.

## 0. Точка отсчёта

Монолит MVP v3: `app.js` ~2227 строк, `style.css` ~1615 строк, `data-sights.js` ~83 строки. Без сборщика, без бэкенда, `localStorage`. Геймификация реализована: ранги (Бронза→Серебро→Золото), чек-листы (15 городов/49 достопримечательностей), 7 состояний маркеров, хроника, ордена.

Корневые проблемы (из `architecture.md §3`):
1. Всё в одном файле, всё глобально
2. Глобальный `state`, прямой доступ отовсюду
3. Ручной `saveState` — забыл = потеря
4. Ручная синхронизация рендера — пропустил = рассинхрон
5. Нет границ — зависимости во все стороны

### Осознанный долг: `style.css` остаётся монолитом на S1

1615 строк стилей в одном файле — второй монолит. В идеальной FSD-архитектуре стили следуют за компонентами (CSS-модули или co-located styles). Однако разделение CSS — это отдельная инициатива, ортогональная распилу JS:
- Распил CSS до распила JS удваивает скоуп S1 и создаёт конфликтующие изменения
- Распил CSS после S1 требует стабильной модульной структуры, которой ещё нет
- Единый `style.css` **работает** — все селекторы глобальны, БЭМ-подобное именование (`.profile-awards`, `.checklist-item`) уже даёт достаточную изоляцию

**Решение:** на S1 `style.css` остаётся единым файлом в `src/`. Слайсы ссылаются на глобальные классы. Разделение стилей — в S3 (`+pages`), когда появится второй экран, требующий независимых стилей. Этот долг зафиксирован явно и не является упущением.

## S1 — Фундамент: рефакторинг + Заметки

### Принципы
1. **Каждая фаза = deployable.** Поведение free-тира не ломается. Smoke-чеклист проходит на каждом шаге.
2. **Импорт только вниз.** `app → widgets → features → entities → shared`. Public API через `index.js`.
3. **Заметки = интеграционный тест S1.** Если лягут чисто — слои выбраны верно. Если нет — ревизия до S2.
4. **Vitest до распила.** Тесты на критические функции пишутся в Phase A, дополняются в каждой фазе.

### Зачем нужен S1

Текущий монолит (`app.js` 2227 строк) работает, но каждая новая фича требует правок в одном файле, где карта знает про чек-листы, а карточка города — про профиль. Добавление платного контента (аудиогиды, маршруты) в такой структуре означает либо усугубление спагетти, либо полное переписывание. S1 решает эту проблему **до** того, как она станет блокером:

- **Распил на слои** даёт границы: изменение в одном слое не ломает другой
- **Store с автосохранением** устраняет баги «забыл сохранить / перерисовать»
- **Vite + ESM** открывают путь к современному toolchain (tree-shaking, HMR, алиасы)
- **Заметки** — первая фича на новом фундаменте, проверяет, что слои работают

### Ключевые архитектурные решения S1

| Решение | Обоснование |
|---|---|
| **Vitest в Phase A** | Распил 2227 строк без тестов — минное поле: ручной smoke-чеклист пропустит регрессию. Тесты на loadState/saveState, инварианты, getCityTier, escapeHtml пишутся ДО распила |
| **XSS-аудит в Phase B** | Ранний аудит безопасности (до того как код разойдётся по слоям) локализует правки. В последней фазе пришлось бы чинить по всем слоям одновременно |
| **Template literals — косметика** | Не влияют на безопасность: `escapeHtml` работает одинаково с `innerHTML` и с template literals. Замена `html +=` — опциональная чистка кода, не блокер |
| **SW network-first в Phase F** | Текущий cache-first SW отдаёт устаревший shell, пользователи не получают обновления. Network-first для HTML решает эту проблему |
| **Детальные критерии «готово»** | Каждая фаза имеет конкретный проверяемый список (grep, тесты, smoke-пункты), а не абстрактное «фаза завершена» |

### Phase A — Vitest + Vite + ESM (поведение без изменений)

**Зачем:** прежде чем резать монолит на куски, нужна страховка. Сейчас любое изменение в `app.js` может сломать что угодно — и мы узнаем об этом только когда пользователь нажмёт не ту кнопку. Vitest даёт автоматическую проверку критических функций (сохранение, ранги, хроника) за секунды, а не за 20 минут ручного smoke-теста. Vite заменяет «file:// открыть в браузере» на нормальный dev-сервер с горячей перезагрузкой и сборкой в `dist/`.

**Цель:** тестовая инфраструктура + модульная загрузка. Код НЕ распиливается.

1. `npm i -D vitest vite` — Vitest + Vite
2. Написать автотесты **до распила** (критические):
   - `loadState` / `saveState` — round-trip с реальными данными localStorage
   - 4 инварианта v3: Gold ∉ planned, Silver ∈ planned, checkedSights только для visited, milestones только для visited
   - `getCityTier` — все 4 ранга (null/bronze/silver/gold)
   - `generateChronicle` — сортировка, milestone-записи
   - `escapeHtml` — XSS-векторы (`<script>`, `&`, `<`, `>`)
3. **Vite-конфигурация:**
   - `vite.config.js` с `base: './'` (деплой в подпапку)
   - `resolve.alias`: `@app` → `src/app`, `@widgets` → `src/widgets`, `@features` → `src/features`, `@entities` → `src/entities`, `@shared` → `src/shared`
   - `public/` директория: `manifest.json`, `sw.js`, `icon-192.svg`, `icon-512.svg`, `covers/` (пустая, заготовка)
   - `build.outDir`: `dist/`
   - `data-sights.js` импортируется как модуль (`import { SIGHTS } from '../data-sights.js'` в Phase A; в Phase B переносится в `entities/sight/` и импорт меняется на `@entities/sight`)
4. `app.js` → `src/app/main.js` (монолитом, как ESM-модуль)
5. `data-sights.js` → `src/data-sights.js` с `export const SIGHTS = {...}`; убрать второй `<script>` из HTML
   - **Временный import в main.js:** `import { SIGHTS } from '../data-sights.js'` (до Phase B, где файл переедет в `entities/sight/` и импорт сменится на `@entities/sight`)
6. `index.html`: `<script type="module" src="/src/app/main.js">`, убрать старый `<script>`
7. `sw.js`: bump `CACHE_NAME` (→ `traveler-passport-v4`); обновить `ASSETS` (пути `src/*`)
   - **Критично:** в `activate`-событии нового SW — явный вызов `caches.delete('traveler-passport-v3')` (старый кэш). Без этого существующие пользователи получат 404 на старые пути (`app.js`, `data-sights.js`) при попытке загрузить старый shell из кэша. Новый SW должен принудительно очистить старый кэш при активации.
8. Прогнать `npm run dev` и `npm run build`; задеплоить `dist/`

**Критерий «готово»:**
- `vitest run` зелёный (тесты на loadState/saveState, инварианты, getCityTier, generateChronicle, escapeHtml)
- `npm run build` собирает `dist/`
- PWA работает офлайн; поток обновления SW (toast «обновлено») срабатывает
- Smoke-чеклист пп. 1–11 проходит
- ~4–5 дней (ориентир)

### Phase C — `app/store.js` (самый хрупкий шаг)

**Зачем:** сейчас состояние приложения — глобальная переменная `state`. Любая функция может поменять её напрямую. Сохранение в localStorage — ручное (`saveState()`): забыл вызвать после изменения = потеря данных. Перерисовка — тоже ручная: изменил состояние, но не вызвал `renderPassport()` = экран рассинхронизирован. Store с автосохранением и подпиской устраняет оба класса багов:

- `setState()` сам сохраняет в localStorage после валидации — невозможно забыть
- `subscribe()` — виджеты автоматически перерисовываются при изменении состояния — невозможно рассинхронизировать

**Цель:** store с автосохранением + subscribe. Замена глобального `state`.

1. Создать `app/store.js`: экземпляр `createStore` + `loadState()` (вся существующая валидация + 4 инварианта v3 as-is) + `saveState()` (8 полей)
2. `setState` автосохраняет в localStorage после валидации
3. `subscribe` — виджеты сами перерисовываются при изменении
4. Заменить глобальный `let state` и ручные `saveState()` на `store.setState(...)`/`store.getState()`
5. Особо проверить:
   - Миграция legacy `currentTab="catalog"` → `"passport"`
   - Dedup `milestones` по cityId+tier
   - Gold-инвариант (Gold ∉ plannedCities)
   - Silver-инвариант (Silver ∈ plannedCities)
   - Старый дамп v0 не падает при импорте

**Критерий «готово»:**
- Все мутации идут через `store.setState`; верифицировано grep-ом: `grep -rn "state\.\w\+\s*=" src/` (исключая `setState`) — пусто
- `vitest run` зелёный; тесты на инварианты, миграцию, round-trip
- Перезагрузка страницы сохраняет состояние
- Smoke-чеклист проходит
- ~4–5 дней (ориентир)

### Phase D1 — Распил `features`

**Зачем:** сейчас бизнес-логика (отметка визита, чек-листы, штампы, планирование, поиск) перемешана с рендерингом в одном файле. Нельзя изменить логику рангов, не затронув карточку города. Features выделяют чистую бизнес-логику: каждый модуль получает store через `init(store)`, работает с ним через `setState`/`getState` и НЕ знает про DOM. Это даёт:

- Изменение логики рангов — в одном файле `features/checklist/`, не затронув карточку
- Тестирование логики отдельно от рендеринга
- Будущие фичи (аудиогиды, маршруты) добавляются как новые features, не трогая существующие

**Цель:** 5 features вынесены, каждый — независимый модуль с `init(store)`.

- `features/visit/` — `confirmVisit`, `removeVisit`, `openDatePicker`, `closeDatePicker`
- `features/checklist/` — `toggleSight`, `addMilestone`/`removeMilestone`/`removeAllMilestones`
- `features/stamps/` — `renderStampOverlay`, `closeStampOverlay`, `goToCollection`, `showShareText`
- `features/plan/` — `togglePlanned` (с tier-aware логикой)
- `features/search/` — фильтры паспорта, `buildSearchResults`, `buildFilterAccordions`

Каждый экспортирует `init(store)` и сам регистрирует слушатели. DI: `app/main.js` прокидывает store.

**Верификация импортов (обязательный шаг):** перед завершением D1 — для каждого файла в `features/` проверить, что все импорты идут только из `entities/` или `shared/` (слой ниже). Ни одного импорта из `widgets/` или `app/`. Скрипт или ручной grep: `import.*from.*widgets` должен быть пуст.

**Критерий «готово»:**
- Все 5 features в `src/features/`
- Импорты features → только entities/shared (верифицировано grep-ом)
- `vitest run` зелёный; тесты на изолированные features
- Smoke-чеклист пп. 1–9, 11, 16 проходят
- ~3–4 дня (ориентир)

### Phase E — Фича «Заметки» (интеграционный тест S1)

**Зачем:** к этому моменту архитектура готова: есть слои, store, features, widgets. Но работают ли они вместе для добавления новой фичи? Заметки — первая функция, которая не существовала в монолите. Если она ложится на слои чисто (4-я вкладка, редактор, быстрая заметка в city-card, миграция старых `cityNotes` → `notes`) — значит архитектура выбрана верно и S2 может начинаться. Если нет — ревизия до перехода к монетизации.

Одновременно Заметки приносят пользователю реальную ценность: сейчас можно писать только одну быструю заметку к городу. После S1 — полноценный блокнот путешественника с поиском, редактором и связью с карточкой города.

**Модель данных:**
```
note = { id, title, body, cityId?, tags?, createdAt: "YYYY-MM-DD", updatedAt: "YYYY-MM-DD" }
state.notes = { [id]: note }
```

**Миграция `cityNotes → notes`** (один раз в `loadState`):
1. Если `state.cityNotes` есть и `state.notes` нет → для каждого cityId создать note `{ id, title: <имя города>, body: cityNotes[cityId], cityId, createdAt/updatedAt = today }`
2. Удалить `cityNotes`, bump версии схемы, сохранить

**Модули:**

| Слой | Модуль | Ответственность |
|---|---|---|
| `entities/note` | `schema`, `isValidNote`, `getNoteById`, `listNotes` | Чистые функции (state аргументом) |
| `features/notes` | `createNote`, `updateNote`, `deleteNote`, `searchNotes`, `getCityNote` | Мутации store через `setState` |
| `widgets/notes-list` | Список, сортировка `updatedAt ↓`, поиск, фильтр, «+ новая» | `init(store)` |
| `widgets/note-editor` | Fullscreen overlay: title/body/city/tags, autosave (debounce 600мс), «удалить» | `init(store)` |
| `widgets/city-card` | (изменение) textarea → `features/notes`; ссылка «открыть в редакторе» | Расширение существующего |
| `app/store` | +`state.notes`, миграция, валидация | Экземпляр store |

**Потоки:**
1. Вкладка → редактор: тап «+» → `createNote({title: ''})` → открыть редактор
2. Редактор → store: input → debounce → `updateNote(id, patch)`. `visibilitychange`/`pagehide` форсируют flush
3. City-card ↔ редактор: textarea при первом символе → `getCityNote(cityId)`; если нет → `createNote({cityId})`
4. Удаление: confirm → `deleteNote(id)` → закрыть редактор → перерисовать список

**Критерий «готово»:**
- Вкладка «Заметки» (4-я): список с поиском, фильтром, «+ новая»
- Редактор: autosave (debounce), удаление с confirm
- Быстрая заметка в city-card ↔ редактор синхронны
- Миграция `cityNotes → notes` для существующих пользователей
- Импорт старого дампа v0 не падает
- `vitest run` зелёный; тесты на entities/note, features/notes, миграцию
- Smoke-чеклист пп. 12–15 проходят
- ~6–7 дней (ориентир)

### Phase F — SW + косметика

**Зачем:** текущий Service Worker использует cache-first стратегию для всего, включая HTML. Это значит, что после деплоя обновлений пользователь продолжает видеть старую версию, пока вручную не очистит кэш или SW не обновится по расписанию браузера (непредсказуемо). Network-first для HTML решает эту проблему: при наличии сети — свежая версия, при отсутствии — закэшированная.

1. `sw.js`: **network-first для HTML/навигации**, cache-first для ассетов — обновления приземляются быстрее
2. Bump `CACHE_NAME` (→ `traveler-passport-v5`)
3. Template literals — по желанию (косметика, не блокер)
4. Прогнать smoke-чеклист в offline-режиме

**Критерий «готово»:**
- Поток обновления SW приземляется быстрее (network-first HTML)
- Smoke-чеклист пп. 10–11 проходят
- ~2–3 дня (ориентир)

## Стратегия ветвления, деплоя и отката (S1)

### Ветвление

Весь S1 выполняется в **одной feature-ветке** (например, `s1-foundation`), которая ответвляется от `main` после §0. Ветвление:

```
main  ──(§0)── ● ────────────────────────────(S1 done)── ● ── merge
                \                                         /
s1-foundation    ●─A─●─B─●─C─●─D1─●─D2─●─E─●─F─────────●
                      ↑ фазы коммитятся с тегами (s1-phase-a, s1-phase-b, …)
```

Каждая фаза коммитится с аннотированным тегом (`git tag -a s1-phase-c -m "S1 Phase C: store"`). Это даёт точки отката: `git reset --hard s1-phase-b`.

### Деплой

- **Промежуточные фазы (A–F)** проверяются локально (`npm run dev` + smoke-чеклист) и на preview-деплое (Vite preview или surge/vercel throwaway). **Не деплоятся в production.**
- **Production-деплой** — только после полного S1, когда все критерии приёмки пройдены и `s1-foundation` смержена в `main`.
- После production-деплоя — мониторинг 48 часов: ошибки в консоли (Sentry или ручной просмотр), жалобы пользователей, регрессии.

### Откат

- **Внутри S1-ветки:** `git reset --hard s1-phase-{X}` — возврат к последней стабильной фазе. Код переписывается заново от точки отката.
- **После мержа в main:** откат через `git revert` мерж-коммита + деплой предыдущего билда. Старый монолит (`app.js`) остаётся в истории — его можно восстановить.
- **Критическое:** фаза C (store) и D2 (удаление app.js) — самые рискованные. Перед ними — ручной бэкап `dist/` предыдущей фазы.

## S2 — Монетизация: аудиогиды (стриминг)

**Зачем:** S1 дал модульную архитектуру. Теперь на неё наслаивается платный контент. Ядро (чек-листы, штампы, карта, заметки) остаётся бесплатным и нетронутым. Платный слой — аудиогиды по городам: пользователь покупает гид, стримит аудио. Деньги идут через нативные покупки (App Store / Google Play), что даёт конверсию в 5–10× выше веб-чекаута. Верификация покупок — через RevenueCat (сервис, который прячет сложность валидации чеков StoreKit/Google Billing). Аудиофайлы хранятся в Cloudflare R2 и отдаются только после проверки права на сервере — клиенту нельзя доверять.

> **Упрощение относительно `monetization.md`:** оффлайн-скачивание (Capacitor Filesystem) и маршруты вынесены в S3. S2 = только «купить → стримить». Это убирает 2 слайса (`download`, `route-follow`) и widget (`route-view`) из S2.

### S2-A0 — Технический спайк (до принятия решения о полном S2)

**Зачем:** Capacitor + RevenueCat + Vite — три технологии, которые никогда не работали вместе в этом проекте. Прежде чем тратить недели на интеграцию, нужно за 1–2 дня проверить, что они совместимы. Если спайк провалится — Plan B (TWA или web-only payments) без потери всего S2.

**Цель:** проверить, что Capacitor + RevenueCat SDK работают с данной кодовой базой и Vite-сборкой, **до** того как вкладывать усилия в полную интеграцию.

1. Создать минимальный Capacitor-проект с одним экраном из кодовой базы (например, карточка города)
2. Подключить `@capacitor-community/purchases` (RevenueCat) плагин
3. Инициализировать RC SDK с sandbox API key
4. Вызвать `getCustomerInfo()` — убедиться, что возвращается пустой entitlement (нет покупок)
5. Проверить: Vite dev-сборка + Capacitor `npx cap sync` + запуск в симуляторе (iOS) / эмуляторе (Android)

**Критерий «готово»:**
- Приложение открывается в симуляторе/эмуляторе
- RC SDK инициализируется без ошибок
- `getCustomerInfo()` возвращает валидный ответ (пустой)
- Vite HMR работает в связке с Capacitor (live reload на симуляторе)
- Решение: «да, Capacitor + RC совместимы с кодовой базой» ИЛИ «найдены блокеры, требующие пересмотра S2»
- **Plan B при провале спайка:** пересмотреть модель распространения. Альтернативы (по убыванию предпочтительности): (1) TWA (Trusted Web Activity) для Android — сохраняет PWA-код без Capacitor, добавляет IAP через Play Billing API; (2) web-only payments (Stripe Checkout + Payment Request API) для обоих платформ; (3) полный отказ от нативного IAP → модель донатов/подписки через веб. Выбор — после анализа причин провала.

**Длительность:** 1–2 дня. **Результат:** gate для перехода к S2-A.

### S2-A — Platform split + Capacitor + RevenueCat

**Зачем:** одна кодовая база должна работать в двух средах — PWA (бесплатный веб, без нативных API) и нативное приложение (с IAP и плеером). Platform split решает это через единый adapter (`app/platform.js`), который включает/отключает фичи в зависимости от среды. Capacitor оборачивает веб-код в нативную оболочку, RevenueCat даёт SDK для покупок. На выходе: PWA не содержит платного кода (безопасность + меньший размер), нативное приложение готово к приёму платежей.

- `app/platform.js` — web vs native: adapter для IAP/FS; что активно в каждой среде
- Capacitor-скаффолд (iOS + Android targets)
- `shared/api/revenuecat.js` — обёртка над Capacitor Purchases plugin
- `app/entitlement.js` — снапшот entitlement (RC getCustomerInfo), subscribe; UI-gating
- PWA-сборка остаётся рабочей (free-тир)

**Релиз:** нативная сборка стартует, RC инициализируется без ошибок; PWA — как раньше.

### S2-B — Gating + Paywall + покупка 1 SKU

**Зачем:** перед тем как создавать контент, нужно построить воронку покупки. Gating (`features/entitlement.getAccess()`) — единая точка, которая решает, показать пользователю контент или paywall. Это критично для безопасности: если gating размазан по виджетам, кто-то забудет проверку — и платный контент утечёт. Paywall — модальное окно с ценой и кнопкой «купить». Один город в качестве тестового SKU позволяет отладить весь flow (нажатие → оплата → entitlement → доступ) до масштабирования на 15 городов.

- `features/entitlement` — `getAccess(contentId)` → bool (ЕДИНАЯ точка gating)
- `features/purchase` — `purchaseCity`/`restore` → revenuecat.js
- `widgets/paywall` — модалка покупки (SKU/цена/IAP)
- Один product ID заведён в App Store Connect/Play + RC (1 город)

**Релиз:** можно купить 1 город (контента ещё нет — только flow); restore работает.

### S2-C — Аудиогид-модель + плеер + gated delivery + R2

**Зачем:** это ядро монетизации — пользователь покупает гид и слушает его. Аудиофайлы (мегабайты `.m4a`) хранятся в Cloudflare R2, а не в репозитории — иначе каждый push тащил бы десятки мегабайт. Доступ к аудио — через подписанные URL: сервер (Cloudflare Worker) проверяет право пользователя через RevenueCat API и только потом отдаёт временную ссылку на файл. Клиент никогда не получает прямой доступ к R2 и не может скачать аудио без покупки. Плеер работает в фоне (media-session) и на экране блокировки — пользователь может слушать гид, свернув приложение.

- `entities/audio-guide` — треки/тайминги/текст (static JSON, `data-audio-guides.js`)
- `features/audio-player` — play/seek/media-session/lock-screen
- `widgets/audio-player-bar` — мини-плеер (фон)
- `shared/api/content.js` — `getSignedAudioUrl(cityId, appUserId)` → CF Worker
- CF Worker: приём RC webhooks → KV (кеш entitlement); проверка права → подписанный URL на R2
- R2 с первым аудио (1 город)
- `widgets/city-card` — + секция «Аудиогид» (gated: купить/слушать)

**Релиз:** купленный гид стримится; некупленный → paywall; запрос без права → Worker 403.

### S2-D — Расширение SKU + бандл + restore

**Зачем:** после отладки на одном городе масштабируемся на все 15. Бандл «вся страна» — пожизненный доступ ко всем гидам по цене 3–4 отдельных городов: мотивирует купить всё сразу, а не по одному. Restore (восстановление покупок) — критично для пользователей, которые меняют телефон или переустанавливают приложение. Без restore они потеряют купленные гиды и уйдут. Soft-prompt «сохранить покупки» привязывает анонимного пользователя к аккаунту через RevenueCat — страховка от потери при смене устройства до того, как появится полноценная система аккаунтов (S4).

- Завести все 15 SKU (по 1 на Топ-15 город) в App Store Connect/Play + RC
- Product `bundle_country` — lifetime-бандл «вся страна»
- Restore-кнопка в профиле
- Soft-prompt: «Сохранить покупки» (RC аноним→идентифицирован) для бэкапа при смене устройства

**Релиз:** полный каталог SKU; бандл открывает все города; restore на чистом устройстве.

### Инварианты безопасности S2 (критично)

1. Клиентский entitlement — **ТОЛЬКО для UI**. Авторизация — исключительно сервер (CF Worker → RC API)
2. Аудио **НИКОГДА не в SW-прекэше** (мегабайты + утечка платного)
3. Единая точка gating — `features/entitlement.getAccess()` — никаких разбросанных проверок
4. Весь сетевой ввод-вывод — в `shared/api/*`; фичи не ходят в сеть напрямую
5. PWA-веб **не содержит** платного контента/логики плеера (platform.js отключает)
