## 0. Почему Phase C — «самый хрупкий шаг»

Из roadmap:
> Сейчас состояние приложения — глобальная переменная `state`. Любая функция может поменять её напрямую. Сохранение в localStorage — ручное (`saveState()`): забыл вызвать после изменения = потеря данных. Перерисовка — тоже ручная: изменил состояние, но не вызвал `renderPassport()` = экран рассинхронизирован.

Phase C устраняет оба класса багов, **но** заменяет ~250 точечных обращений к `state` в `main.js`. Каждое обращение — потенциальный источник регрессии. Поэтому:

1. **Замена механическая**, не архитектурная — каждое `state.X` → `store.getState().X`, каждое `state.X[Y] = Z` → `store.setState(prev => …)`
2. **Тесты пишутся/переносятся ДО большого рефакторинга** — они ловят регрессии
3. **Grep-проверка** (`tools/check-mutations.mjs`) — финальный gate

## 1. Главное архитектурное решение

**`src/app/store.js`** — единый модуль, экспортирующий синглтон `store`:

```js
// src/app/store.js — публичный API
export const store;                          // экземпляр createStore
export function loadState();                 // первичная загрузка из localStorage
export const STORAGE_KEY;                    // константа
```

Внутреннее устройство:
- Использует `createStore` из `@shared/lib/store-mechanism.js`
- Доменная валидация (4 инварианта) применяется на каждом `setState`
- Персистенция в `localStorage` через адаптер `{ key, getItem, setItem }` (НЕ `localStorage` напрямую — см. TODO в `store-mechanism.js`)
- Ошибки записи → `onError` → тост `'Не удалось сохранить данные. Освободите место в браузере.'`

**Файлы, которые меняются:**
- ✅ **Создаётся** `src/app/store.js`
- ✅ **Удаляется** `src/lib/storage.js` (код переезжает в `app/store.js`)
- ✅ **Обновляется** `src/lib/milestones.js` (функции становятся чистыми)
- ✅ **Обновляется** `src/app/main.js` (~250 точечных правок)
- ❌ **НЕ трогается** `src/shared/lib/store-mechanism.js` (Phase B уже создал, Phase C использует as-is)

### 2.2. Контракт `applyInvariants(next, prev)`

**Принятое решение: `applyInvariants` мутирует входной `next`** (как в текущем `loadState`).

**Обоснование мутации (а не immutable):**
1. Поведение идентично существующему `loadState` (минимизация рисков регрессии)
2. Вызывается ТОЛЬКО из `createStore.validate` — гарантированно получает свежий объект `next` (созданный внутри `setState` через `{ ...state, ...patch }` или возвращённый функцией-updater'ом)
3. Сложность O(N) на инварианты; возврат нового объекта не даёт выигрыша (создание нового CITIES.length = 57 итераций для #2 идентично по стоимости)

**Контракт:**
- Принимает `(next, prev)` — для совместимости с сигнатурой `createStore.validate(next, prev)`. Аргумент `prev` не используется, но принимается.
- **Мутирует `next`**: удаляет/добавляет ключи в `plannedCities`, удаляет ключи из `checkedSights`, пересоздаёт массив `milestones`
- Возвращает тот же `next` (для совместимости с `createStore`)
- Никогда не выбрасывает (no throw) — инварианты не должны ломать приложение

```js
function applyInvariants(next, _prev) {
  // #1: Gold ∉ plannedCities
  for (var cityId in next.plannedCities) {
    if (getCityTier(cityId, next, SIGHTS) === "gold") {
      delete next.plannedCities[cityId];
    }
  }
  // #2: Silver ∈ plannedCities
  for (var i = 0; i < CITIES.length; i++) {
    if (getCityTier(CITIES[i].id, next, SIGHTS) === "silver") {
      next.plannedCities[CITIES[i].id] = true;
    }
  }
  // #3: checkedSights только для visited
  for (var cityId in next.checkedSights) {
    if (!next.visitedCities[cityId]) {
      delete next.checkedSights[cityId];
    }
  }
  // #4: milestones только для visited
  next.milestones = next.milestones.filter(function (m) {
    return next.visitedCities[m.cityId];
  });
  return next;
}
```

> **Предупреждение:** в комментарии в коде ОБЯЗАТЕЛЬНО указать:
> ```js
> // ВАЖНО: мутирует `next`. Вызывать ТОЛЬКО из createStore.validate.
> // Никогда не вызывать напрямую из main.js или тестов с произвольным state,
> // если state используется где-то ещё — будет повреждён.
> // Для unit-тестов — передавать свежий объект.
> ```

### 2.3. Разделение валидации: load vs setState

| Тип | Где | Что делает |
|---|---|---|
| **Тяжёлая** (типы, cityId, sightId, dedup) | `validateDump(saved)` в `loadState()` | Проверяет корректность сохранённого дампа. Вызывается **один раз** при инициализации. |
| **Лёгкая** (4 инварианта) | `applyInvariants(state)` в `validate` callback `createStore` | Гарантирует консистентность. Вызывается **на каждом setState**. |

**Обоснование:** `validateDump` слишком дорог для каждого setState (проходит по всем массивам, проверяет типы). А инварианты — дешёвые и ловят «грязные» мутации (например, добавление Gold города в plannedCities). Доверие к mutation-путям в плане типов — прагматичный компромисс. Если в будущем появится неизвестный источник мутаций — добавится более строгая валидация.

### 2.4. Первичная загрузка

`readFromStorage()`:
```js
function readFromStorage() {
  try {
    const raw = localStorage.getItem(STORAGE_KEY);
    if (!raw) return withEphemeral(getDefaultState());
    const saved = JSON.parse(raw);
    const validated = validateDump(saved);
    if (validated._needsResave) {
      // Что-то было исправлено — пересохранить
      setTimeout(() => {
        try { localStorage.setItem(STORAGE_KEY, JSON.stringify(validated._cleanState)); }
        catch (e) { /* silent */ }
      }, 0);
    }
    return withEphemeral(validated._cleanState);
  } catch (e) {
    return withEphemeral(getDefaultState());
  }
}
```

**Поведение идентично текущему `loadState`** (Phase B).

### 2.5. Persist-адаптер (критично!)

Из TODO в `store-mechanism.js`:
> ⚠️ `persist` НЕ равно `localStorage`. Передать `localStorage` напрямую — нельзя: у него есть метод `key(n)`, который затенит строковое поле `key`.

Поэтому адаптер оборачивает `getItem`/`setItem`:
```js
const persistAdapter = {
  key: STORAGE_KEY,
  getItem: (k) => localStorage.getItem(k),
  setItem: (k, v) => localStorage.setItem(k, v)
};
```

### 2.6. ⚠️ Подводный камень: shallow merge вложенных объектов

В `createStore` (Phase B) `setState` делает:
```js
const next = typeof patch === 'function' ? patch(state) : { ...state, ...patch };
```

Это **shallow merge** — для вложенных объектов (`plannedCities`, `visitedCities`, `checkedSights`, `cityNotes`, `milestones`) `patch` **ЗАМЕНЯЕТ** целиком, а не мержит.

**Пример БАГА:**
```js
// ❌ НЕПРАВИЛЬНО — стирает все остальные планы:
store.setState({ plannedCities: { minsk: true } });

// ✅ ПРАВИЛЬНО — функция-updater возвращает полный nextState:
store.setState(function (prev) {
  return { ...prev, plannedCities: { ...prev.plannedCities, minsk: true } };
});

// ✅ ТАКЖЕ ПРАВИЛЬНО — caller вычисляет полный новый объект заранее:
var nextPlanned = Object.assign({}, store.getState().plannedCities, { minsk: true });
store.setState({ plannedCities: nextPlanned });
```

**Безопасные случаи** (только скаляры):
- `currentTab`, `travelerName`, `onboardingComplete`, `passportFilter`, `passportSearchQuery`, `mapFilter`, `stampOrigin`, `stampOverlayCityId`, `activeOverlayCityId`

**Опасные случаи** (объекты/массивы):
- `visitedCities`, `plannedCities`, `checkedSights`, `cityNotes`, `openedRegions`, `milestones`

**Правило для реализации:** для всех «опасных» полей использовать функцию-updater или предварительно вычислить полный новый объект. Документировать в JSDoc каждого `store.setState` в main.js.

### 3.2. Чтения (state.X → store.getState().X)

**~150 read-сайтов.** Механическая замена:

```js
// ─── Read ───
// До:
var isVisited = !!state.visitedCities[cityId];
// После:
var isVisited = !!store.getState().visitedCities[cityId];

// До:
html += '    <span class="profile-name-text">' + escapeHtml(state.travelerName) + '</span>';
// После:

```

**Стратегия минимизации diff:** ввести локальные переменные для часто используемых state-полей:

```js
function switchTab(tabId) {
  const state = store.getState();   // кэш на время выполнения
  if (state.currentTab === "passport") { ... }
  // ...
}
```

Но **не** делать модульный `let state` или module-level cache. Только внутри функций — чтобы grep `state\.\w+\s*=` оставался пустым (за исключением локальных переменных).

### 3.3. Записи (state.X = Y → store.setState(prev => ...))

**~60 write-сайтов.** Используем хелперы:

#### Простое присваивание (state.X = Y)

```js
// До:
state.currentTab = tabId;

// После:
store.setState({ currentTab: tabId });
```

#### Вложенное присваивание (state.X[Y] = Z)

```js
// До:
state.plannedCities[cityId] = true;

// После (через updateMap):
store.setState(function (prev) {
  return updateMap(prev, 'plannedCities', function (m) {
    return Object.assign({}, m, { [cityId]: true });
  });
});
```

Или короче, через spread:
```js
store.setState(function (prev) {
  return {
    ...prev,
    plannedCities: { ...prev.plannedCities, [cityId]: true }
  };
});
```

#### Удаление из map (delete state.X[Y])

```js
// До:
delete state.plannedCities[cityId];

// После:
store.setState(function (prev) {
  return updateMap(prev, 'plannedCities', function (m) {
    return omitKey(m, cityId);
  });
});
```

#### Несколько мутаций в одной функции

```js
// До (togglePlanned, ~3 мутации):
if (state.plannedCities[cityId]) {
  delete state.plannedCities[cityId];
} else {
  state.plannedCities[cityId] = true;
}
saveState();

// После (ОДИН setState):
store.setState(function (prev) {
  const planned = prev.plannedCities;
  const nextPlanned = planned[cityId]
    ? omitKey(planned, cityId)
    : Object.assign({}, planned, { [cityId]: true });
  return { ...prev, plannedCities: nextPlanned };
});
```

**Это важно:** несколько мутаций в одной функции = **один** `setState`. Иначе между setState'ами вызываются subscribers (если есть) и валидация, что может быть неожиданным поведением.

### 3.4. Мутации через `lib/milestones.js`

`addMilestone`, `removeMilestone`, `removeAllMilestones` сейчас мутируют `state.milestones.push(...)`. В Phase C они становятся чистыми.

**Изменение в `src/lib/milestones.js`:**

```js
// До:
export function addMilestone(state, cityId, tier) {
  if (tier !== "silver" && tier !== "gold") return;
  var exists = state.milestones.some(m => m.cityId === cityId && m.tier === tier);
  if (!exists) {
    state.milestones.push({ cityId, date: getTodayLocal(), tier });
  }
}

// После (ВСЕГДА возвращает новый объект, даже при dedup — для предсказуемости ссылок):
export function addMilestone(state, cityId, tier) {
  if (tier !== "silver" && tier !== "gold") {
    return { ...state, milestones: state.milestones };  // shallow clone для единообразия
  }
  var exists = state.milestones.some(function (m) {
    return m.cityId === cityId && m.tier === tier;
  });
  if (exists) {
    return { ...state, milestones: state.milestones };  // тоже новый объект (но тот же массив)
  }
  return {
    ...state,
    milestones: state.milestones.concat([{ cityId: cityId, date: getTodayLocal(), tier: tier }])
  };
}

// Аналогично для removeMilestone, removeAllMilestones — всегда возвращают новый объект.
```

| `state.cityNotes[cityId] = trimmed` (1 место) | присваивание | spread |
| `delete state.cityNotes[cityId]` (1 место) | delete | omitKey |

**Где объединять:** функции с несколькими мутациями (например, `confirmVisit`, `removeVisit`, `togglePlanned`, `toggleSight`, `saveNote`) — **один** `setState` с комплексным updater'ом.

  if (isProcessing) return;
  isProcessing = true;
  try {
    var state = store.getState();
    var isVisited = !!state.visitedCities[cityId];
    var sightIds = SIGHTS[cityId];
    if (!isVisited || !sightIds || !sightIds.some(s => s.id === sightId)) return;

    var nextChecked = currentChecked.includes(sightId)
      ? currentChecked.filter(id => id !== sightId)
      : [...currentChecked, sightId];

      nextState = addMilestonePure(nextState, cityId, "silver");
    } else if (oldTier !== "gold" && newTier === "gold") {
      nextState = addMilestonePure(nextState, cityId, "gold");
    } else if (oldTier === "silver" && newTier === "bronze") {
      nextState = removeMilestonePure(nextState, cityId, "silver");
    } else if (oldTier === "gold" && newTier === "silver") {
      nextState = removeMilestonePure(nextState, cityId, "gold");
    } else if (oldTier === "silver" && newTier === "gold") {
      nextState = addMilestonePure(nextState, cityId, "gold");

    // НЕ обновлять plannedCities вручную здесь — applyInvariants в createStore.validate
    // применит инварианты #1 (Gold ∉ plannedCities) и #2 (Silver ∈ plannedCities)

    store.setState(nextState);  // ← ОДИН setState с полным nextState

## 6. Тесты — переезд и новые

### 6.0. Стратегия изоляции тестов для store-синглтона

**Проблема:** `src/app/store.js` экспортирует синглтон `store` (строка 90 плана), инициализируется при импорте модуля. Без сброса состояния между тестами:
- `store.setState(...)` мутирует state — следующий тест видит «грязное» состояние
- `store.subscribe(...)` накапливает подписчиков — `unsubscribe` не помогает, если тест забыл отписаться
- `beforeEach(() => localStorage.clear())` сбрасывает только localStorage, **не** in-memory state

Тесты будут flaky: порядок выполнения влияет на результат.

**Решение:** метод `__resetForTest()` (см. §2.1) + общий `tests/setup.js`.

**Реализация:**

```js
// tests/setup.js (дополнение к существующему)
import { beforeEach } from 'vitest';
import { __resetForTest } from '../src/app/store.js';

beforeEach(async () => {
  localStorage.clear();
  await __resetForTest();   // сбрасывает in-memory state + subscribers
});
```

**Использование в тестах:**

```js
// tests/app/store-autosave.test.js
import { store } from '../../src/app/store.js';

describe('store autosave', () => {
  // beforeEach уже настроен в tests/setup.js — каждый тест получает чистый store
  
  it('setState вызывает localStorage.setItem', () => {
    const setItem = vi.spyOn(Storage.prototype, 'setItem');
    store.setState({ currentTab: 'profile' });
    expect(setItem).toHaveBeenCalledWith('travelerPassport', expect.stringContaining('"currentTab":"profile"'));
  });
});
```

**Альтернативы (отклонены):**
- **vi.resetModules() + динамический import** — усложняет код тестов (async setup, динамические пути)
- **Factory pattern `createAppStore()`** — чище архитектурно, но требует рефакторинга в main.js (`const store = createAppStore()` вместо singleton-импорта). Перенос в Phase D2 (когда store будет переиспользоваться в виджетах).

**Что НЕ тестирует `__resetForTest`:**
- Не сбрасывает моки (`vi.spyOn`) — их нужно восстанавливать вручную (`vi.restoreAllMocks()` в `afterEach` или в самом тесте)
- Не сбрасывает `vi.fn()` — они сбрасываются автоматически между тестами Vitest

**Покрытие `__resetForTest` (новый тест):**
```js
// tests/app/store-reset.test.js

describe('__resetForTest', () => {
  it('сбрасывает state к свежему из localStorage', () => {
    store.setState({ currentTab: 'map' });
    expect(store.getState().currentTab).toBe('map');
    
    localStorage.clear();
    __resetForTest();
    
    expect(store.getState().currentTab).toBe('passport');  // дефолт
  });
  
  it('очищает subscribers', () => {
    const sub = vi.fn();
    store.subscribe(sub);
    __resetForTest();
    
    store.setState({ currentTab: 'map' });
    expect(sub).not.toHaveBeenCalled();  // подписчик удалён
  });
});
```

## 7. Grep-проверка `tools/check-mutations.mjs`

```js
// tools/check-mutations.mjs
import { readFileSync } from 'node:fs';

const mainJs = readFileSync(new URL('../src/app/main.js', import.meta.url), 'utf-8');

// Ищем все `state.X = Y` или `state.X[Y] = Z` (mutations)
const mutationRegex = /\bstate\.\w+\s*(?:\[.*?\])?\s*=(?!=)/g;
const matches = [...mainJs.matchAll(mutationRegex)];

// Исключения: возможно, разрешены в комментариях (// ...)
const realMatches = matches.filter(m => {
  const lineStart = mainJs.lastIndexOf('\n', m.index) + 1;
  const lineEnd = mainJs.indexOf('\n', m.index);
  const line = mainJs.slice(lineStart, lineEnd === -1 ? undefined : lineEnd);
  return !line.trim().startsWith('//');
});

if (realMatches.length > 0) {
  console.error(`Найдено ${realMatches.length} прямых мутаций state в main.js:`);
  realMatches.forEach(m => {
    const lineNum = mainJs.slice(0, m.index).split('\n').length;
    console.error(`  строка ${lineNum}: ${m[0]}`);
  });
  process.exit(1);
}
console.log('OK: нет прямых мутаций state в main.js');
```

## 13. Шпаргалка: API `store` после Phase C

```js
import { store, loadState, STORAGE_KEY, applyInvariants } from '@app/store.js';

// Чтение:
const state = store.getState();         // snapshot
const isVisited = !!store.getState().visitedCities[cityId];

// Мутация скаляра (OK — простой merge):
store.setState({ currentTab: 'map' });

// ⚠️ Мутация вложенного объекта — НЕЛЬЗЯ через простой patch (см. §2.6):
// store.setState({ plannedCities: { minsk: true } });  // ❌ стирает остальные планы!

// ✅ Правильно для вложенных объектов — функция-updater:
store.setState(function (prev) {
  return {
    ...prev,
    visitedCities: { ...prev.visitedCities, [cityId]: { date: '2025-01-01' } },
    plannedCities: omitKey(prev.plannedCities, cityId)
  };
});

// Subscribe (Phase D2):
const unsub = store.subscribe(function (newState) {
  renderProfile();
});
unsub();
```

**Полный список «опасных» полей** (объекты/массивы — всегда функция-updater): `visitedCities`, `plannedCities`, `checkedSights`, `cityNotes`, `openedRegions`, `milestones`.
