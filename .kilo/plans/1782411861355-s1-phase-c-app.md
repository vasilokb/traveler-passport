## 0. Почему Phase C — «самый хрупкий шаг»

Из roadmap:
> Сейчас состояние приложения — глобальная переменная `state`. Любая функция может поменять её напрямую. Сохранение в localStorage — ручное (`saveState()`): забыл вызвать после изменения = потеря данных. Перерисовка — тоже ручная: изменил состояние, но не вызвал `renderPassport()` = экран рассинхронизирован.

Phase C устраняет оба класса багов, **но** заменяет ~250 точечных обращений к `state` в `main.js`. Каждое обращение — потенциальный источник регрессии. Поэтому:

1. **Замена механическая**, не архитектурная — каждое `state.X` → `store.getState().X`, каждое `state.X[Y] = Z` → `store.setState(prev => …)`
2. **Тесты пишутся/переносятся ДО большого рефакторинга** — они ловят регрессии
3. **Grep-проверка** (`tools/check-mutations.mjs`) — финальный gate

## 1. Главное архитектурное решение

**`src/app/store.js`** — единый модуль, экспортирующий синглтон `store`:

**Публичный API модуля (сигнатуры — НЕliteral-код):**
```js
// src/app/store.js — публичный API (эти строки — ОПИСАНИЕ экспортов, не literal JS)
// export const store              → экземпляр createStore (инициализируется при объявлении, см. ниже)
// export function loadState()     → первичная загрузка из localStorage
// export const STORAGE_KEY        → константа "travelerPassport"
//
// ⚠️ ВАЖНО: `export const store;` (без инициализатора) — СИНТАКСИЧЕСКАЯ ОШИБКА.
// Реальный код инициализирует store при объявлении:
//   export const store = createStore({ ... });  // см. реализацию ниже (§2.1, строка ~156)
//   export const STORAGE_KEY = "travelerPassport";
```

Внутреннее устройство:
- Использует `createStore` из `@shared/lib/store-mechanism.js`

- Ошибки записи → `onError` → тост `'Не удалось сохранить данные. Освободите место в браузере.'`

## 2. Архитектура `src/app/store.js`

### 2.1. Структура файла

```js
// src/app/store.js
import { createStore } from '@shared/lib/store-mechanism.js';
import { CITIES, getCityById, getCityTier } from '@entities/city/index.js';
import { SIGHTS } from '@entities/sight/index.js';

export const STORAGE_KEY = "travelerPassport";

// ─── Дефолтное состояние (8 сохраняемых полей) ───
function getDefaultState() { /* ... */ }

// ─── Финализация (добавление 6 эфемерных полей) ───
// ВАЖНО: переименование `finalize` (Phase B, src/lib/storage.js:24) → `withEphemeral` (Phase C).
// Тело 1:1, только имя лучше отражает контракт: «обернуть в state с эфемерными полями».
function withEphemeral(state) { /* возвращает новый объект с добавленными ephemeral */ }

// ─── Валидация сохранённого дампа (тяжёлая, при load) ───
// ⚠️ КОНТРАКТ: строит _cleanState ТОЛЬКО из 8 сохраняемых полей (см. PERSIST_FIELDS
// ниже). Неизвестные/лишние ключи в `saved` (в т.ч. эфемерные поля, которые могли
// случайно попасть в дамп) — ИГНОРИРУЮТСЯ. Это защита от утечки эфемерных полей
// (mapFilter, openedRegions) в state при загрузке. Возвращает { _cleanState, _needsResave }.
function validateDump(saved) { /* типы, cityId, sightId, dedup; только 8 полей */ }

// ─── 4 инварианта v3 (лёгкие, при каждом setState) ───
export function applyInvariants(state) { /* мутирует state (или возвращает новый) */ }

// ─── Загрузка из localStorage (ПУБЛИЧНАЯ функция для тестов) ───
// Это та же функция, что инициализирует store при импорте модуля.
// Экспортируется, чтобы тесты могли:
//   1) перезагрузить state из localStorage после установки тестовых данных
//   2) тестировать миграцию legacy-дампов изолированно от store
//
// Сигнатура: `loadState({ storage } = {})` — опциональный storage для тестов.
// В production вызывается без аргументов; в тестах передаётся `localStorage`.
export function loadState({ storage = localStorage } = {}) {
  try {
    const raw = storage.getItem(STORAGE_KEY);
    if (!raw) return withEphemeral(getDefaultState());
    const saved = JSON.parse(raw);
    const validated = validateDump(saved);
    if (validated._needsResave) {
      setTimeout(function () {
        try { storage.setItem(STORAGE_KEY, JSON.stringify(validated._cleanState)); }
        catch (e) { /* silent */ }
      }, 0);
    }
    return withEphemeral(validated._cleanState);
  } catch (e) {
    return withEphemeral(getDefaultState());
  }
}

// ─── Сохраняемые поля (ровно 8; всё остальное — эфемерное) ───
// ⚠️ Сверено с app.js:848-857 (saveState toSave). Эфемерные поля (mapFilter,
// openedRegions, passportFilter, passportSearchQuery, stampOverlayCityId,
// activeOverlayCityId, stampOrigin) НЕ персистятся в v3. createStore пишет
// persist через JSON.stringify(state) — полный объект (все 14 полей). Чтобы
// дамп localStorage совпадал с v3 (поведение 1:1), persistAdapter.setItem
// обязан отфильтровать до 8 полей. Без фильтрации mapFilter и openedRegions
// «протекают» в дамп → переживают перезагрузку → visible behavior change
// (фильтр карты и раскрытые регионы остаются между сессиями, чего в v3 нет).
const PERSIST_FIELDS = [
  'currentTab', 'travelerName', 'onboardingComplete',
  'visitedCities', 'plannedCities', 'cityNotes',
  'checkedSights', 'milestones'
];

// ─── Persist-адаптер (НЕ localStorage напрямую!) ───
// ⚠️ `persist` НЕ равно `localStorage` — у localStorage есть метод `key(n)`,
// который затенит строковое поле `key` адаптера. Поэтому оборачиваем.
// ⚠️ setItem ФИЛЬТРУЕТ полный state до 8 полей (поведение 1:1 с v3 saveState).
//    createStore передаёт сюда JSON.stringify(state) — все 14 полей;
//    без фильтрации эфемерные поля утекли бы в дамп.
const persistAdapter = {
  key: STORAGE_KEY,
  getItem: function (k) { return localStorage.getItem(k); },
  setItem: function (k, v) {
    try {
      var full = JSON.parse(v);
      var toSave = {};
      for (var i = 0; i < PERSIST_FIELDS.length; i++) {
        var f = PERSIST_FIELDS[i];
        if (full[f] !== undefined) toSave[f] = full[f];
      }
      localStorage.setItem(k, JSON.stringify(toSave));
    } catch (e) {
      // fallback: записать как есть (лучше мусор, чем потеря данных)
      localStorage.setItem(k, v);
    }
  }
};

// ─── Tост при ошибке записи ───
function showSaveError() { /* showToast('Не удалось сохранить...') */ }

// ─── Store instance ───
// `loadFromPersist: false` — см. §2.5.1: createStore НЕ должен перезаписывать
// наш валидированный initialState сырым JSON из persist.
// `initialStateLoader: loadState` — для `_resetForTest()`: при вызове тестами
// store перечитывает localStorage через loadState() (см. §6.0).
export const store = createStore({
  initialState: loadState(),
  validate: applyInvariants,
  persist: persistAdapter,
  loadFromPersist: false,
  initialStateLoader: loadState,
  onError: function (e, op) {
    if (op === 'persist') showSaveError();
    // 'load' и 'validate' ошибки — silent (loadState уже fallback на default,
    // validate не должен бросать — инварианты безопасны)
  }
});

// ─── Хелперы для immutable updates ───
// `setKey` и `updateMap` НЕ экспортируются — в main.js используется
// pattern spread (`{ ...prev, plannedCities: ... }`) напрямую (см. §3.3).
// Они остались здесь как заготовка для Phase D2 (когда виджеты начнут
// инкапсулировать сложные мутации в переиспользуемые хелперы).
function setKey(state, key, value) {
  return Object.assign({}, state, { [key]: value });
}
function updateMap(state, key, updater) {
  return Object.assign({}, state, { [key]: updater(state[key]) });
}

// `omitKey` ЭКСПОРТИРУЕТСЯ — используется КАК в `src/app/main.js` (§3.3, §5.1,
// §5.3, §5.4: togglePlanned, confirmVisit, removeVisit, saveNote — все 4 операции
// требуют delete-операций на вложенных map-ах), ТАК И в тестах
// (tests/app/store-flow.test.js — для воспроизведения removeVisit-flow без UI).
export function omitKey(obj, key) {
  var copy = {};
  for (var k in obj) {
    if (Object.prototype.hasOwnProperty.call(obj, k) && k !== key) {
      copy[k] = obj[k];
    }
  }
  return copy;
}

// `_resetForTest` ЭКСПОРТИРУЕТСЯ — re-export из store для использования в tests/setup.js.
// Подробнее — см. комментарий ниже.
export const _resetForTest = store._resetForTest;

// ─── Test-only API (используется ТОЛЬКО в тестах через `tests/setup.js`) ───
// ВАЖНО: подчёркивание в имени — маркер «не использовать в production коде».
// Метод сбрасывает in-memory state к loadState() + очищает subscribers.
// Нужен потому, что store — синглтон, и без сброса тесты будут flaky.
//
// Реализация (5 строк в createStore):
//   function _resetForTest() {
//     state = opts.initialStateLoader ? opts.initialStateLoader() : state;
//     subscribers.clear();
//   }
//   return { getState, setState, subscribe, _resetForTest };
//
// В app/store.js `initialStateLoader` — это `loadState`.
// При вызове _resetForTest() store перечитывает localStorage через loadState().
//
// Ре-экспорт для тестов:
//   export const _resetForTest = store._resetForTest;
//
// Это МИНИМАЛЬНОЕ расширение createStore (не рефакторинг), оправданное нуждами тестирования.
// Альтернатива (vi.resetModules + динамический import) значительно усложняет тесты
// и была отклонена в §6.0 как менее читаемая.
//
// Покрывается тестом: reset очищает state и subscribers.
```

**Документированные значения `op` в `onError`:**
- `'load'` — ошибка при загрузке из persist.getItem (JSON.parse упал, нет прав доступа и т.п.). Phase C не использует — loadFromPersist отключён.
- `'validate'` — ошибка в user-provided validate callback. Phase C не выбрасывает (инварианты безопасны), но если кто-то добавит throw — сюда попадёт.
- `'persist'` — ошибка при записи в persist.setItem (например, QuotaExceededError). Триггерит тост.

### 2.2. Контракт `applyInvariants(next, prev)`

**Принятое решение: `applyInvariants` мутирует входной `next`** (как в текущем `loadState`).

**Обоснование мутации (а не immutable):**
1. Поведение идентично существующему `loadState` (минимизация рисков регрессии)
2. Вызывается ТОЛЬКО из `createStore.validate` — гарантированно получает свежий объект `next` (созданный внутри `setState` через `{ ...state, ...patch }` или возвращённый функцией-updater'ом)
3. Сложность O(N) на инварианты; возврат нового объекта не даёт выигрыша (создание нового CITIES.length = 57 итераций для #2 идентично по стоимости)

**Контракт:**
- Принимает `(next, prev)` — для совместимости с сигнатурой `createStore.validate(next, prev)`. Аргумент `prev` не используется, но принимается.
- **Мутирует `next`**: удаляет/добавляет ключи в `plannedCities`, удаляет ключи из `checkedSights`, пересоздаёт массив `milestones`
- Возвращает тот же `next` (для совместимости с `createStore`)
- Никогда не выбрасывает (no throw) — инварианты не должны ломать приложение

```js
function applyInvariants(next, _prev) {
  // #1: Gold ∉ plannedCities
  for (var cityId in next.plannedCities) {
    if (getCityTier(cityId, next, SIGHTS) === "gold") {
      delete next.plannedCities[cityId];
    }
  }
  // #2: Silver ∈ plannedCities
  for (var i = 0; i < CITIES.length; i++) {
    if (getCityTier(CITIES[i].id, next, SIGHTS) === "silver") {
      next.plannedCities[CITIES[i].id] = true;
    }
  }
  // #3: checkedSights только для visited
  for (var cityId in next.checkedSights) {
    if (!next.visitedCities[cityId]) {
      delete next.checkedSights[cityId];
    }
  }
  // #4: milestones только для visited
  next.milestones = next.milestones.filter(function (m) {
    return next.visitedCities[m.cityId];
  });
  return next;
}
```

> **Предупреждение:** в комментарии в коде ОБЯЗАТЕЛЬНО указать:
> ```js
> // ВАЖНО: мутирует `next`. Вызывать ТОЛЬКО из createStore.validate.
> // Никогда не вызывать напрямую из main.js или тестов с произвольным state,
> // если state используется где-то ещё — будет повреждён.
> // Для unit-тестов — передавать свежий объект.
> ```

### 2.3. Разделение валидации: load vs setState

| Тип | Где | Что делает |
|---|---|---|
| **Тяжёлая** (типы, cityId, sightId, dedup) | `validateDump(saved)` в `loadState()` | Проверяет корректность сохранённого дампа. Вызывается **один раз** при инициализации. |
| **Лёгкая** (4 инварианта) | `applyInvariants(state)` в `validate` callback `createStore` | Гарантирует консистентность. Вызывается **на каждом setState**. |

**Обоснование:** `validateDump` слишком дорог для каждого setState (проходит по всем массивам, проверяет типы). А инварианты — дешёвые и ловят «грязные» мутации (например, добавление Gold города в plannedCities). Доверие к mutation-путям в плане типов — прагматичный компромисс. Если в будущем появится неизвестный источник мутаций — добавится более строгая валидация.

### 2.4. Первичная загрузка — публичная `loadState()`

`loadState({ storage } = {})` — публичная функция (экспортируется), реализация описана в §2.1. Здесь — обзор контракта и поведения:

```js
// Сигнатура:
export function loadState({ storage = localStorage } = {}) {
  try {
    const raw = storage.getItem(STORAGE_KEY);
    if (!raw) return withEphemeral(getDefaultState());
    const saved = JSON.parse(raw);
    const validated = validateDump(saved);
    if (validated._needsResave) {
      // Что-то было исправлено — пересохранить асинхронно
      setTimeout(function () {
        try { storage.setItem(STORAGE_KEY, JSON.stringify(validated._cleanState)); }
        catch (e) { /* silent */ }
      }, 0);
    }
    return withEphemeral(validated._cleanState);
  } catch (e) {
    return withEphemeral(getDefaultState());
  }
}
```

**Поведение идентично текущему `loadState`** (Phase B). Возвращает полный state со всеми 6 эфемерными полями. Параметр `storage` нужен ТОЛЬКО для тестов — в production всегда используется `localStorage`.

> ⚠️ **Отклонение тайминга resave (зафиксировано в §17):** v3 (Phase A `storage.js:185`) вызывает `saveState()` **синхронно** внутри `loadState` при `needsFix`. Phase C заменяет это на `setTimeout(..., 0)` (асинхронно), потому что `loadState` выполняется ДО создания store (передаётся как `initialState: loadState()`) и не может вызвать `store.setState`. На практике безвредно: `loadState` вызывается один раз при `init`, ничего не читает `localStorage` синхронно после возврата. Через один тик мигрированный дамп перезаписан. Тесты с миграцией должны использовать `vi.useFakeTimers()` + `vi.runAllTimers()` (см. §6.0, Паттерн А).

### 2.5. Persist-адаптер (критично!)

Из TODO в `store-mechanism.js`:
> ⚠️ `persist` НЕ равно `localStorage`. Передать `localStorage` напрямую — нельзя: у него есть метод `key(n)`, который затенит строковое поле `key`.

Поэтому адаптер оборачивает `getItem`/`setItem` (см. полную реализацию в §2.1, включая обязательную фильтрацию 8 полей в `setItem`):

```js
const persistAdapter = {
  key: STORAGE_KEY,
  getItem: (k) => localStorage.getItem(k),
  setItem: (k, v) => {
    // Фильтруем полный state до 8 полей (поведение 1:1 с v3 saveState).
    // createStore передаёт сюда JSON.stringify(всё состояние); без фильтрации
    // эфемерные mapFilter/openedRegions утекли бы в дамп → поведение-отклонение.
    // Полная реализация + PERSIST_FIELDS — см. §2.1.
  }
};
```

> **⚠️ Фильтрация в `setItem` ОБЯЗАТЕЛЬНА** (исправление при ревью плана). `createStore` (Phase B) вызывает `persist.setItem(key, JSON.stringify(state))` — сериализуя ВСЕ 14 полей. v3 `saveState` фильтровал до 8 (`app.js:848–857`). Без фильтрации: `mapFilter` и `openedRegions` переживают перезагрузку (через `withEphemeral`: `state.mapFilter || "all"`, `state.openedRegions || []` читают сохранённое значение). Это **видимое пользователю поведение-отклонение**, ломающее «поведение 1:1». Тест: `tests/app/store-persist.test.js` — после `setState({ mapFilter: 'visited', openedRegions: ['minsk'] })` + reload → дамп содержит ТОЛЬКО 8 полей (нет `mapFilter`/`openedRegions`); после перезагрузки mapFilter=`"all"`, openedRegions=`[]`.

### 2.5.1. Опция `loadFromPersist: false` в `createStore`

**Проблема, найденная при ревью плана:**

`createStore` из Phase B (`store-mechanism.js:21-28`) после установки `initialState` ВЫЗЫВАЕТ `persist.getItem(persist.key)` и при truthy-результате **затирает** state сырым `JSON.parse(...)`:
```js
if (persist && persist.key) {
  var raw = persist.getItem(persist.key);
  if (raw) state = JSON.parse(raw);   // ← сырой JSON, без validate
}
```

Но план §2.1 передаёт `initialState: loadState()` — уже валидированное состояние с применёнными инвариантами. Если `getItem` вернёт truthy (raw JSON из localStorage), `createStore` **перезапишет** валидированный state сырым невалидированным дампом. **Все 4 инварианта и тяжёлая `validateDump` обходятся на init.**

**Решение (принятое):** добавить в `createStore` опцию `loadFromPersist` (default `true` для обратной совместимости):

```js
// src/shared/lib/store-mechanism.js (минимальное дополнение, ~3 строки)
var shouldLoadFromPersist = opts.loadFromPersist !== false;  // default true
if (shouldLoadFromPersist && persist && persist.key) {
  try {
    var raw = persist.getItem(persist.key);
    if (raw) state = JSON.parse(raw);
  } catch (e) {
    if (onError) onError(e, 'load', null);
  }
}
```

В `app/store.js`:
```js
export const store = createStore({
  initialState: loadState(),          // наша валидированная загрузка
  validate: applyInvariants,
  persist: persistAdapter,
  loadFromPersist: false,             // ← отключаем createStore's auto-load
  initialStateLoader: loadState,      // ← для _resetForTest
  onError: (e, op) => { ... }
});
```

**Почему не `getItem: () => null` workaround:** текущая фаза C и так трогает `createStore` для `_resetForTest` (§2.1). Добавить `loadFromPersist` — это **+3 строки** против сохранения неуклюжего workaround, документирующего баг вместо его исправления. Семантика явная: «я сам управляю загрузкой».

**Тест:** `tests/shared/store-mechanism.test.js` — кейс «loadFromPersist: false» — initialState сохраняется даже при наличии persist.getItem.

### 2.6. ⚠️ Подводный камень: shallow merge вложенных объектов

В `createStore` (Phase B) `setState` делает:
```js
const next = typeof patch === 'function' ? patch(state) : { ...state, ...patch };
```

Это **shallow merge** — для вложенных объектов (`plannedCities`, `visitedCities`, `checkedSights`, `cityNotes`, `milestones`) `patch` **ЗАМЕНЯЕТ** целиком, а не мержит.

**Пример БАГА:**
```js
// ❌ НЕПРАВИЛЬНО — стирает все остальные планы:
store.setState({ plannedCities: { minsk: true } });

// ✅ ПРАВИЛЬНО — функция-updater возвращает полный nextState:
store.setState(function (prev) {
  return { ...prev, plannedCities: { ...prev.plannedCities, minsk: true } };
});

// ✅ ТАКЖЕ ПРАВИЛЬНО — caller вычисляет полный новый объект заранее:
var nextPlanned = Object.assign({}, store.getState().plannedCities, { minsk: true });
store.setState({ plannedCities: nextPlanned });
```

**Безопасные случаи** (только скаляры):
- `currentTab`, `travelerName`, `onboardingComplete`, `passportFilter`, `passportSearchQuery`, `mapFilter`, `stampOrigin`, `stampOverlayCityId`, `activeOverlayCityId`

**Опасные случаи** (объекты/массивы):
- `visitedCities`, `plannedCities`, `checkedSights`, `cityNotes`, `openedRegions`, `milestones`

**Правило для реализации:** для всех «опасных» полей использовать функцию-updater или предварительно вычислить полный новый объект. Документировать в JSDoc каждого `store.setState` в main.js.

```js
// До:
export function addMilestone(state, cityId, tier) {
  if (tier !== "silver" && tier !== "gold") return;
  var exists = state.milestones.some(m => m.cityId === cityId && m.tier === tier);
  if (!exists) {
    state.milestones.push({ cityId, date: getTodayLocal(), tier });
  }
}

// После (dedup = возврат state as-is; реальное добавление = новый объект):
export function addMilestone(state, cityId, tier) {
  if (tier !== "silver" && tier !== "gold") return state;  // no-op, возвращаем state
  var exists = state.milestones.some(function (m) {
    return m.cityId === cityId && m.tier === tier;
  });
  if (exists) return state;  // dedup — state as-is (избегаем лишней записи в persist + subscribers)
  return {
    ...state,
    milestones: state.milestones.concat([{ cityId: cityId, date: getTodayLocal(), tier: tier }])
  };
}

// removeMilestone, removeAllMilestones — см. «Контракт» ниже (ВАЖНО: не 1:1 с addMilestone).
```

**Контракт `removeMilestone`/`removeAllMilestones` (⚠️ отличается от `addMilestone`):**

Реальный оригинал (`app.js:646–665`) **НЕ проверяет**, было ли удаление — он ВСЕГДА создаёт новый массив и переприсваивает (`state.milestones = filtered`). Таким образом контракт чистой версии — на выбор реализации:

| Вариант | Поведение | Ссылочная идентичность |
|---|---|---|
| **(а) Буквальное воспроизведение кода** | Всегда `return { ...state, milestones: filteredArray }` (даже если `filteredArray.length === state.milestones.length`) | `next !== state` всегда |
| **(б) no-op-оптимизация** | Если ничего не удалено → `return state`; иначе новый объект | `next === state` при no-op, `next !== state` при удалении |

**Оба варианта допустимы** — на поведение приложения это не влияет: `setState` всё равно вызовет `persist.setItem` и `subscribers` (т.к. `createStore` из Phase B НЕ имеет оптимизации `next === state`, см. обоснование ниже). Разница — только в тестовом ассерте: `toBe(state)` vs `not.toBe(state)`.

**Требование:** реализация и тесты в §6.2 должны быть согласованы. Агент выбирает ОДИН вариант и реализует + тестирует именно его:
- если (а) — тест проверяет `expect(next.milestones).toHaveLength(...)` + `expect(next).not.toBe(state)` всегда;
- если (б) — тест добавляет кейс «no-op: несуществующий milestone → `expect(next).toBe(state)`» (как для `addMilestone` dedup, §6.2).

**Рекомендация (прагматичная):** вариант **(б) no-op-оптимизация** — единообразие с `addMilestone`, меньше лишних persist-записей при toggleSight-флоу (где `removeMilestone` часто вызывается на уже отсутствующем milestone). В этом случае контракт всех трёх функций единый: «almost pure — не мутирует, возвращает `state` as-is при no-op, иначе новый объект».

> ⚠️ **Не-воспроизведение как регрессия:** выбор варианта (б) при убирании milestone, который ЕСТЬ в state — это не отклонение поведения (milestone реально удаляется). Только no-op-случай (убираем того, чего нет) меняет ссылочную идентичность относительно оригинала, но `setState` это маскирует. Поэтому §17 (отклонения) НЕ затрагивается.

**Обоснование возврата `state` as-is при dedup/no-op (для addMilestone и варианта (б) remove*):**
1. ⚠️ **Исправление при ревью:** `createStore` из Phase B НЕ имеет оптимизации `next === state` — persist.write и subscribers срабатывают ВСЕГДА (безусловно), даже если `patch(state)` вернул ту же ссылку. Таким образом, возврат `state` as-is при dedup — это no-op-запись в localStorage + лишний notify подписчиков (безвредно, но НЕ «бесплатно»). Чтобы реально пропускать no-op, нужно добавить `if (validated === state) return;` в `createStore.setState` (Phase D2 рассмотрит). Для Phase C это допустимо: dedup случается редко (только когда milestone уже есть), а запись идентичного дампа в localStorage безвредна.
2. **Контракт:** "almost pure" — функция никогда не мутирует, но может вернуть `state` as-is при no-op. Тесты могут проверять `expect(next).toBe(state)` для dedup и `expect(next).not.toBe(state)` для реального добавления. ВАЖНО для тестов: `expect(next).toBe(state)` проверяет, что функция вернула входную ссылку (no-op), а НЕ что persist не сработал (он сработает).

**Изменение в `src/app/main.js`** (обёртки):

## 6. Тесты — переезд и новые

### 6.0. Стратегия изоляции тестов для store-синглтона

**Проблема:** `src/app/store.js` экспортирует синглтон `store` (строка ~92 плана), инициализируется при импорте модуля. Без сброса состояния между тестами:
- `store.setState(...)` мутирует state — следующий тест видит «грязное» состояние
- `store.subscribe(...)` накапливает подписчиков — `unsubscribe` не помогает, если тест забыл отписаться
- `beforeEach(() => localStorage.clear())` сбрасывает только localStorage, **не** in-memory state

Тесты будут flaky: порядок выполнения влияет на результат.

**Решение:** метод `_resetForTest()` (см. §2.1 — реализуется через минимальное дополнение `createStore`) + общий `tests/setup.js`.

**Реализация:**

```js
// tests/setup.js (дополнение к существующему)
import { beforeEach } from 'vitest';
import { _resetForTest } from '../src/app/store.js';

beforeEach(() => {
  localStorage.clear();
  _resetForTest();   // сбрасывает in-memory state + subscribers (синхронно)
});
```

**⚠️ ВНИМАНИЕ: race с `_needsResave` setTimeout.**

`loadState()` (см. §2.4) при обнаружении мигрируемого дампа запускает `setTimeout(..., 0)` для авто-пересохранения. Если тест:
1. Устанавливает `localStorage.setItem(...)` с legacy-данными (catalog→passport и т.п.)
2. Вызывает `_resetForTest()` → store вызывает `loadState()` → запускает `setTimeout(..., 0)` для resave
3. Затем сразу проверяет `localStorage.getItem(...)` → **может быть ещё пустым** (setTimeout не сработал)
4. Через несколько миллисекунд — значение появляется (мигрированный дамп перезаписан)

**Решение для тестов с legacy-данными:**

```js
// Паттерн А: использовать vi.useFakeTimers() и прокручивать таймеры
import { vi } from 'vitest';
beforeEach(() => { vi.useFakeTimers(); });
afterEach(() => { vi.useRealTimers(); });

it('legacy migration', () => {
  localStorage.setItem(STORAGE_KEY, JSON.stringify({ currentTab: 'catalog', ... }));
  _resetForTest();  // запускает setTimeout
  vi.runAllTimers();  // ← прокручиваем setTimeout
  const raw = localStorage.getItem(STORAGE_KEY);
  expect(JSON.parse(raw).currentTab).toBe('passport');  // мигрировано
});

// Паттерн Б: тестировать loadState() напрямую (без store-reset), проверяя только _cleanState
const state = loadState();
expect(state.currentTab).toBe('passport');
// Resave через setTimeout НЕ проверяем (это побочный эффект)

// Паттерн В: await микротаска
await new Promise(r => setTimeout(r, 0));
const raw = localStorage.getItem(STORAGE_KEY);
```

**Рекомендация:** для тестов, проверяющих миграцию, использовать **Паттерн Б** (прямой вызов `loadState()`, не `_resetForTest`). Для тестов autosave/subscribe — **Паттерн А** (`vi.useFakeTimers`).

**⚠️ ВАЖНО для `store-load.test.js` (исправление при ревью плана):**

Тесты на `loadState()` / миграцию legacy дампов требуют особого порядка:
1. **Сначала** устанавливают `localStorage.setItem(...)` с тестовыми данными
2. **Затем** вызывают `_resetForTest()` — store перечитывает localStorage через `loadState()` (через `initialStateLoader`)

Если порядок нарушен (например, тест забыл `_resetForTest` после установки localStorage), `store.getState()` покажет данные из ПРЕДЫДУЩЕГО теста или дефолт.

**Правильный паттерн для тестов с предустановленным localStorage:**

- Не сбрасывает моки (`vi.spyOn`) — их нужно восстанавливать вручную (`vi.restoreAllMocks()` в `afterEach` или в самом тесте)
- Не сбрасывает `vi.fn()` — они сбрасываются автоматически между тестами Vitest

```js
  });

  it('не удаляет ключи из прототипа (hasOwnProperty)', () => {
    const proto = { inherited: 'value' };
    const input = Object.create(proto);
    input.own = 1;

    expect(result).toHaveProperty('inherited');  // унаследованные — не в result, но и не «удалены» (это прототип)
    expect(result).not.toHaveProperty('own');
  });

  it('пустой объект → пустой объект', () => {
    expect(omitKey({}, 'any')).toEqual({});
  });

  it('несуществующий ключ → без изменений', () => {
    const result = omitKey({ a: 1 }, 'nonexistent');
    expect(result).toEqual({ a: 1 });
```

```js
describe('confirmVisit flow (end-to-end на applyInvariants level)', () => {
  // НЕ использует store (избегаем singleton-isolation проблем).

      checkedSights: {},

    // given: город посещён, 1 пункт из 4 отмечен
    const next = applyInvariants({
      visitedCities: { minsk: { date: '2025-01-15' } },
      plannedCities: {},
      checkedSights: { minsk: ['s0'] },  // 1 из 4
      milestones: [],
      // ... ephemeral defaults
      currentTab: 'passport', travelerName: '', onboardingComplete: true,
      cityNotes: {}

    expect(next.plannedCities.minsk).toBe(true);
    expect(next.milestones).toHaveLength(1);
    expect(next.milestones[0]).toMatchObject({ cityId: 'minsk', tier: 'silver' });

  it('Silver → Gold (отметка всех пунктов) → milestone=Gold, plannedCities удалён', () => {

      plannedCities: { minsk: true },
      checkedSights: { minsk: ['s0', 's1', 's2'] },

        ...before,
        checkedSights: { minsk: ['s0', 's1', 's2', 's3'] },  // все 4
      },
      'minsk',
      'gold'
    );
    const afterWithInvariants = applyInvariants(after, null);

    // then:

    expect(afterWithInvariants.milestones).toHaveLength(2);  // silver + gold
    expect(afterWithInvariants.milestones.find(m => m.tier === 'gold')).toBeDefined();
  });

  it('removeVisit: очищает visited + checkedSights + planned + milestones', () => {
    const before = {
      visitedCities: { minsk: { date: '2025-01-15' } },
      plannedCities: { minsk: true },
      checkedSights: { minsk: ['s0', 's1', 's2', 's3'] },

      checkedSights: omitKey(before.checkedSights, 'minsk'),

      milestones: before.milestones.filter(m => m.cityId !== 'minsk'),

    const finalState = applyInvariants(after, null);

    expect(finalState.visitedCities.minsk).toBeUndefined();
    expect(finalState.checkedSights.minsk).toBeUndefined();
    expect(finalState.plannedCities.minsk).toBeUndefined();
    expect(finalState.milestones).toHaveLength(0);
  });
});
```

```js
// tools/check-mutations.mjs
import { readFileSync } from 'node:fs';

const mainJs = readFileSync(new URL('../src/app/main.js', import.meta.url), 'utf-8');

// Ищем все `state.X = Y` или `state.X[Y] = Z` (mutations)
const mutationRegex = /\bstate\.\w+\s*(?:\[.*?\])?\s*=(?!=)/g;
const matches = [...mainJs.matchAll(mutationRegex)];

// Исключения: возможно, разрешены в комментариях (// ...)
const realMatches = matches.filter(m => {
  const lineStart = mainJs.lastIndexOf('\n', m.index) + 1;
  const lineEnd = mainJs.indexOf('\n', m.index);
  const line = mainJs.slice(lineStart, lineEnd === -1 ? undefined : lineEnd);
  return !line.trim().startsWith('//');
});

if (realMatches.length > 0) {
  console.error(`Найдено ${realMatches.length} прямых мутаций state в main.js:`);
  realMatches.forEach(m => {
    const lineNum = mainJs.slice(0, m.index).split('\n').length;
    console.error(`  строка ${lineNum}: ${m[0]}`);
  });
  process.exit(1);
}
console.log('OK: нет прямых мутаций state в main.js');
```

```js
// ⚠️ Мутация вложенного объекта — НЕЛЬЗЯ через простой patch (см. §2.6):

// ✅ Правильно для вложенных объектов — функция-updater:
store.setState(function (prev) {
  return {
    ...prev,
    visitedCities: { ...prev.visitedCities, [cityId]: { date: '2025-01-01' } },
```
